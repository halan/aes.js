# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Didactic AES-128 implementation in ES6, written in a functional style. README is explicit: **not for production** — favors readability over efficiency or security. Most source comments are in pt-BR; preserve language and style when editing.

## Commands

- Run all tests: `npm test` (mocha 11)
- Run a single test file: `npx mocha test/aes/expandKey_test.js`
- Generate annotated docs: `npm run doc` (docco → `docs/` from the pt-BR comments)

The project is ESM (`"type": "module"` in package.json). Tests import the source via the `imports` subpath map (`#aes`, `#aes/expandKey`, `#aes/rounds/index`, `#opModes`, `#utils`, `#padding`) — that map replaces the old `NODE_PATH=./src` trick. Source files use relative imports with explicit `.js` extensions, as ESM requires.

## Architecture

Entry point `src/index.js` exposes two namespaces: `AES` (raw block cipher) and `OpModes` (block-mode wrappers + padding). They are composed by the caller — `OpModes.cbc(AES.encrypt(key), iv)` returns a function from plaintext to ciphertext.

### Functional pipeline style

Everything is built on `pipe(...fns)(x)` from `src/utils.js`. Each AES step is a pure function `Buffer → Buffer` (or array → array), composed left-to-right. When reading or modifying code, trace data flow through `pipe(...)` rather than looking for imperative state. Helpers in `utils.js` worth knowing:

- `pipe`, `map`, `reduce`, `flat`, `reverse` — pipe-friendly curried versions
- `partition(n)` / `splitInWords` — group a flat array into chunks (words = 4 bytes)
- `xor(left)(right)` — byte-wise XOR
- `chainBlocks(fn)(ini)` / `chainBlocksInv` — fold where each step's output feeds the next; used both by CBC and by `expandKey`

### AES core (`src/aes/`)

- `aes/index.js` — top-level `encrypt(key)` / `decrypt(key)`. Both follow the same shape: `expandKey` → first round → 9 middle rounds → last round. Decrypt uses the inverse rounds and `expandKey(key).reverse()`.
- `aes/expandKey.js` — Rijndael key schedule. Only AES-128 (11 round keys). If extending to AES-192/256, the `RCON` table and the `[key, ...keys]` assembly are the touch points.
- `aes/rounds/index.js` — assembles `firstRound`, `middleRound`, `lastRound` and their `*Inv` variants from the four step modules. Note: `firstRound === addRoundKey` and `lastRoundInv === addRoundKey` (commutative, no inverse needed). The last round skips `mixColumns`.
- `aes/rounds/{subBytes,shiftRows,mixColumns,addRoundKey}.js` — each exports the forward op and its inverse. `mixColumns` uses precomputed Galois multiplication tables (G2/G3 for encrypt, G9/G11/G13/G14 for decrypt) — these are lookup tables, not to be regenerated by hand.

### Modes & padding (`src/opModes.js`, `src/padding.js`)

`opModes.js` exports `ecb` / `ecbInv` / `cbc` / `cbcInv`. They take an `encrypt` (or `decrypt`) function — the curried `AES.encrypt(key)` — plus an IV for CBC, and return `Buffer → Buffer`. PKCS#7 (spelled `pksc7` in the code) is applied before encryption and stripped after decryption.

Known rough edges to be aware of when working here (per the last commit message, padding validation is intentionally absent):

- `pksc7Inv` trusts the last byte blindly — no validation of padding correctness
- `ecbInv` in `opModes.js` calls `inBlocks(16)` and `encrypt` — neither is in scope (likely a bug from the CBC refactor); ECB decrypt is not exercised by tests

### Tests (`test/`)

Mirror the `src/` tree (`test/aes/rounds/*_test.js` matches `src/aes/rounds/*.js`). Mocha + chai BDD style. The `npm test` glob only descends three levels — keep that in mind if adding deeper directories.
